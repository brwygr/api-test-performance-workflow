# JMeter 条件迁移指南

## 触发与边界

仅在用户明确要求导入、转换、运行 JMeter 或排查 JMX 时加载。本文件列出交付要求；不要在用户只做 Apifox 时提前加入另一套学习任务。基于确认的当前请求、配置和成功响应生成实际方案，不承诺直接导出就必然可运行。

迁移前集中补齐：来源文件与目标版本、Java/JMeter 安装与启动方式、目标环境、认证数据来源、数据文件位置、已授权负载。列出导出不包含或不能自动迁移的内容。

## 1. 一次性交付迁移对照表

每行填写“原配置 → JMeter 组件/字段 → 本次具体值/来源 → 修改内容 → 验收”。未知必填项先确认，不能留下未解释的空值让用户直接运行。

| 项目 | JMeter 映射与必须说明的差异 |
| --- | --- |
| 服务地址 | HTTP Request 的 Protocol、Server、Port、Path；建议拆字段，Server 不含协议，Path 保留约定前缀 |
| 方法与 Query | Method 和 Parameters；每个参数的变量、类型、启用及编码；核对最终查询串 |
| Body | Parameters、Body Data 或文件上传；JSON、urlencoded、multipart 分别设置，不能混用 |
| Headers/Auth | HTTP Header Manager 及合适的认证组件；Bearer 是否重复、多个服务鉴权字段各自来自哪里 |
| Cookie | 是否需要 HTTP Cookie Manager、清理时机及用户会话隔离；按真实认证确定 |
| 请求行为 | Content encoding、连接/响应超时、重定向、代理、证书、keepalive 与原请求是否一致 |
| 变量 | 每个 `{{name}}` 映射 `${name}`，写出初始来源、作用域、消费者与更新点 |
| 前后置 | 按功能迁移成提取器、断言或 JSR223；逐段注明是否替换、位置和完整代码 |
| 数据 | CSV/文件的实际路径、编码、列名、分隔符、线程分配与 EOF 行为 |
| 负载 | Thread Group 的线程、启动、循环、持续时间、Timer 节奏、Sampler 失败后的策略；不能把线程数当成 QPS |
| 输出 | 样本标签、JTL 内容与路径、日志、HTML 报告目录及所需统计项 |

HTTP Request 允许 Path 为完整 URL；该模式会忽略其他地址字段，并影响 GET/DELETE 参数表的使用。为了减少歧义可统一用拆字段方式，但不能说完整 URL 一律非法。必须核对实际 URL 和 Query。[J1]

## 2. 变量、认证与持久化

- 检索 JMX 中全部 Apifox 花括号、空鉴权和硬编码旧数据。`${name}` 未定义时可能原样留下，检查非空还不够，须检查占位符残留与实际解析值。[J2]
- 静态初始值可用 User Defined Variables 或属性；UDV 不能替代每轮动态提取。运行变量 `vars` 属于当前线程，`props` 是共享属性；给出每个变量的所有者与更新位置。[J2]
- setUp Thread Group 的 `vars` 不能直接当成业务线程的变量使用。若集中初始化，明确结果传递与身份隔离；单用户只读 Token 的共享也须解释有效期。不得共享会轮换的 refresh 给并发线程。
- 对每线程独立认证，使用适当的线程内初始化、条件控制器、提取器和刷新逻辑。CSV 每轮是否切换身份要按实际读取与循环设置说明；不能从行里每轮重新装回已失效的旧 refresh。
- JSON Extractor 先提取到候选变量，并明确提取路径、匹配规则、默认失败标记；检查 HTTP、业务条件和所有必要字段后才更新正式变量。失败保留有效值并记录可解释错误。[J1]
- **JMeter 后置处理器先于断言执行**。不能以“稍后的断言会检查”为理由提前覆盖 Token。负责写入的处理器内必须自行验证成功条件。[J3]
- 不把 Apifox 的 `pm.*` 脚本原样粘入 JMeter。按真实字段提供完整 JSR223 Groovy 代码或提取器配置，逐段列出位置、作用范围与启用状态；Groovy 脚本通过 `vars.get(...)` 读取运行值，避免将动态 `${...}` 直接插入缓存脚本文本。[J4]
- JMeter 运行变量不自动成为下次运行的初始值。使用轮换凭据时必须明确跨运行保存方案、唯一写入者和失败恢复；认证初始化成功后即应保留最新凭据，不能等整场业务成功才保存。共享文件写入须解决并发，不能各线程覆盖同一行。

不能根据通用说明生成万能认证脚本。每条认证链须有实际请求、响应结构、提取与刷新规则；没有依据就把这项列为待确认。

## 3. 数据文件与线程

列出 CSV Data Set Config 的文件名与路径、编码、Variable Names、是否忽略首行、分隔符、Sharing mode、Recycle on EOF 与 Stop thread on EOF，说明这些值对本次账号/资源绑定的影响。路径以当前机器和执行方式验证，不依赖另一台机器的原始绝对路径。[J1]

同一账号对应的 Token、用户 ID 与资源 ID 要保持关联；多用户测试不能只增加线程却仍混用同一组账号数据。多个线程组、循环边界和文件结束行为都须纳入说明。共用账号的热点测试可以保留，但报告写清其范围。

## 4. 可交付的计划结构

按当前任务生成实际组件树，并标注所有脚本与配置的作用范围。例如，仅在需要时采用：

```text
Test Plan
└─ Thread Group（用户与循环模型）
   ├─ HTTP Request Defaults（本场景服务）
   ├─ CSV Data Set Config（需要多组数据时）
   ├─ HTTP Header Manager / Cookie Manager（按实际依赖）
   ├─ 初始化/按需认证（有明确触发和持久化方案时）
   └─ 目标业务请求
      ├─ 提取器 / JSR223 PostProcessor（需要时）
      └─ HTTP 与业务断言
```

不能把某个服务专用鉴权头不加区分地放在覆盖所有域名的父级。思考时间/Timer 的作用范围也要标明，避免不小心延迟所有初始化和认证请求。

明确本次采用固定次数还是持续运行。有限循环与持续时间/结束时间哪个先到就结束，有限循环跑完不会自动补足设定时长；持续运行时须配合相应循环设置。列明 Sampler 出错后继续、进入下一轮、停止线程或停止测试的实际策略，并检查认证失败是否导致线程提前退出。[J1]

## 5. 调试、运行和输出

1. 离线检查 XML、变量引用、插件依赖、数据路径、脚本和组件启用状态。
2. 经确认后以 GUI 单线程单次检查实际请求、响应、断言、提取和数据关联；已有充分证据时不额外轮换凭据。
3. 根据确认的负载使用命令行运行。负载时避免启用 View Results Tree 等高开销监听器；记录 Java/JMeter 版本和插件依赖。[J5]
4. 给出符合用户系统的完整命令与真实路径，并一次列出需要替换的内容。以下只是生成命令的结构，不能让用户直接复制占位路径：

```powershell
& 'C:\实际安装位置\apache-jmeter\bin\jmeter.bat' -n -t 'E:\实际项目\计划.jmx' -l 'E:\实际项目\本次唯一运行目录\samples.jtl' -j 'E:\实际项目\本次唯一运行目录\jmeter.log' -e -o 'E:\实际项目\本次唯一运行目录\html'
```

5. 输出父目录应已创建且可写；HTML 目标目录须为空或不存在。每次生成唯一运行路径，避免混入旧样本。需要参数化时列出每个 `-J` 属性与计划中的读取点，不把凭据无必要地放进命令行。[J5]
6. 说明查看 JTL、日志和报告的方法。完成后核对实际目标样本数、业务通过率、实际持续时间、吞吐与耗时分位。GUI 单次通过不等于完成压测。

## 6. 交付验收

- 迁移差异表无未解释的必填项，Apifox 占位符与脚本 API 已正确迁移。
- 计划、数据与脚本路径可用；无未声明插件依赖；没有复用失效的静态 refresh。
- 最终请求 URL、参数、鉴权和账号资源一致，HTTP 与业务条件均有判定。
- 凭据更新不被失败响应覆盖；需要时有跨运行保存方案。
- 已执行的最小验证有实际样本；负载报告有正确范围与实际负载证据。
- 交代已做的验证和未执行的检查。成功只说明本次条件下的结果，不能归因另一工具之前的故障。
