# Apifox 完整配置与交付模板

## 使用方法

用于已确认资料的调试、认证或自动化任务。以下变量名、路径和处理器只是编写配置单的示例槽位；依据真实接口选取，不能原样当作现成项目导入。已存在且有效的配置优先复用。只说明与当前接口相关的内容。

## 1. 资料与配置概况

先交代：目标环境、工具版本、采用的文件及时间、接口/场景范围、哪些内容尚未包含在导出中。文件修改时间只能用于辅助定位，不能证明文件内容就是当前有效配置。

把资料归纳成“当前值/证据/是否需修改”，再给下列配置表。对仍未知但必填的项先集中询问，不交付声称可运行的半成品。

## 1.1 JSON 文件位置与域名填写

在指导导入、覆盖或执行前，必须先明确以下信息；不能只告诉用户“导入 JSON”或“填域名”：

| 项 | 需要确认或从已授权资料整理的内容 | 验收方式 |
| --- | --- | --- |
| JSON 来源 | 文件名、完整路径、来源（Apifox 导出/项目文件/HAR 转换/其他）、导出时间或版本线索 | 能打开并解析结构；说明是否包含接口、环境、场景、脚本和断言 |
| JSON 存放位置 | 导入前的原文件位置、导入到哪个 Apifox 项目/目录、修改后是否另存及保存路径、是否允许覆盖旧文件 | 明确“读取哪个、写入哪个、是否覆盖”；未实际写入时不能声称已保存 |
| 目标环境 | 环境名称、运行时选中的环境、是否为本地/测试/预发/正式 | 运行前核对实际选中的环境和变量解析值 |
| 业务域名 | 协议、主机名、端口、路径前缀；对应哪个环境变量 | 查看最终解析后的业务 URL，无残留 `{{变量}}`、错误协议或重复前缀 |
| 认证域名 | 是否与业务域名不同；认证请求使用的完整地址和变量 | 分别核对认证请求与业务请求，不能把两个域名合并成一个变量 |
| 其他域名 | 第三方、文件、链节点或回调服务是否存在 | 只保留实际请求需要的域名，并标明消费者 |
| JSON 中的地址 | 文件内已有的 base URL、Host 或服务器项 | 与当前目标环境和成功请求对照后决定保留、替换或待确认，不能按文件名猜测 |

### 处理规则

1. 用户已提供项目目录、JSON 或明确授权读取时，先列出候选文件，读取 JSON 的顶层结构、接口数量、环境/服务器字段和域名集合；不要先要求用户重复截图。
2. 只能从已授权文件和当前成功请求中确定的值直接填入。发现多个环境、多个服务器或业务/认证域名不一致时，先给出对照表并一次性询问选择。
3. 域名填写必须说明“填在哪里”：例如环境变量的本地值、远程值、接口服务器配置、认证接口 URL 或请求级覆盖；同时说明是否需要解除本地值与远程值的关联。
4. 导入前说明匹配与覆盖范围：新建、更新同名接口、覆盖环境、是否包含场景/脚本；导入预览与文件路径不一致时停止覆盖。
5. 修改后提供保存位置和回读验证；如果只是修改了本地 JSON 或草稿，没有实际导入 Apifox，明确写出这一点。

域名与 JSON 路径属于配置前置条件，应在环境变量、请求参数和脚本说明之前一次列清；后续若出现新环境或新服务，再补充对应差异，不重复让用户重新整理全部配置。

## 2. 环境变量一次列全

| 变量名 | 本次值或精确来源 | 必填性 | 初始化/生成与时机 | 使用位置 | 存储与作用域 | 保存与验证 |
| --- | --- | --- | --- | --- | --- | --- |
| `api_base_url`（示例） | 当前环境确认的服务前缀 | 按接口确定 | 初始化 | 最终请求 URL | 指定环境；本地/远程关系见下表 | 核对最终完整 URL |
| `access_token`（示例） | 已确认的登录/刷新响应的具体字段 | 按鉴权确定 | 初始取得；后置更新 | Authorization 或真实鉴权位置 | 指定环境本地值或场景变量 | 有效值检查；必要时验证跨运行保存 |
| `refresh_token`（仅需要时） | 实际刷新凭据及字段路径 | 按认证流程确定 | 初始化；成功刷新后可能轮换 | 只用于刷新请求 | 明确唯一有效存储和并发使用者 | 保存最新成功返回值 |
| 业务标识（示例 `resource_id`） | 列表接口提取规则或确认的测试数据 | 按请求确定 | 初始化或前一步生成 | Query/Path/Body 指定位置 | 明确环境/场景/循环作用域 | 核对归属、环境和数据隔离 |

表中还应包含本项目实际需要的客户端标识、第三方服务地址/凭据、网络、分页、测试数据文件等。接口不需要的变量不添加。区分业务 Token、第三方 Token 和 Cookie，不能仅凭变量名或 JWT 外观推断用途。

### 本地值、远程值与关联

Apifox 环境/全局变量支持本地值和远程值；本地值可选择关联远程值，解除关联后可独立修改。脚本修改变量值作用于本地值。会话变量只在所属运行中有效。具体解析还受同名变量作用域影响，必须核对实际请求和当前作用域。[S1]

| 使用情形 | 本项目应给的建议 | 必须验证的点 |
| --- | --- | --- |
| 团队共同使用的稳定地址/公共常量 | 需要跟随团队配置时保留关联；个人覆盖时另行确定 | 选对环境/服务模块；远程当前值符合本次目标 |
| 当前机器使用且运行中更新的凭据 | 需要独立维护本地值时解除对应变量的关联 | 实际写入和读取的是同一变量、同一环境；不依赖空的远程值 |
| 当前场景临时提取的数据 | 生命周期只需本轮时用相应运行作用域 | 不把运行结束后消失当成持久化故障 |

**不能一律要求解除所有变量的关联。**对每个相关变量明确写“保留/解除/待确认”和原因；不要把同一轮换 refresh 同时作为两个会被独立使用的当前值。若存在环境、全局、场景、循环或数据文件同名项，列出实际来源并消除意外遮蔽。

持久化要分别说明：手工编辑后如何保存；脚本写入的作用域；场景运行配置是否启用了“保存变量值”及选定环境；运行后在哪里核对。官方场景运行文档列出了保存变量值的运行设置，具体界面和效果需按当前版本检查。[S2]

变量被遮罩与变量为空是两回事。核对解析后的发送内容，必要时检查存在性、长度、占位符是否残留。验证保存优先使用无副作用的检查变量和重新打开配置；已有有效凭据时不要为了测保存连续调用轮换接口。

## 3. 请求参数与实际 URL

每个目标请求都给出下表，不只列新增的一个参数：

| 项 | 本次完整配置 | 依据与检查 |
| --- | --- | --- |
| 方法与地址 | Method、服务模块、环境前置 URL、请求路径、最终 URL | 核对协议、域名、端口、路径前缀组合一次；不得出现重复协议、重复前缀或未替换变量 |
| Path 参数 | 名称、示例值/来源、必填性 | 注意占位位置与 URL 编码 |
| Query 参数 | 名称、类型、值/变量、必填性与是否启用 | 不能把业务 ID、第三方 ID 和钱包地址等当成可互换标识 |
| Headers 与 Auth | 名称、鉴权配置、值格式、变量来源 | 避免 Auth 页和手工 Header 重复设置；Bearer 前缀是否包含在变量中只约定一次 |
| Body | JSON/表单/urlencoded/文件；字段、类型、必填性 | Content-Type 与实际编码匹配；GET 是否有 Body 按契约确认 |
| Cookie | 是否需要、来源、Cookie 管理器行为 | 不盲目复制整份浏览器历史 Cookie |
| 请求行为 | 重定向、代理、证书、超时等实际相关设置 | 只保留确有依赖的配置 |

前置 URL 可以包含约定的路径前缀，不强制必须只有主机名。使用服务模块前缀或完整变量 URL 时，明确哪一种组合方式生效。浏览器当前成功请求比历史 HAR 更能说明当前环境，但仍需确认账号和目标。

一般让客户端生成 Host、Content-Length 等传输字段；如果确需手动设置，说明原因并验证。不要用旧 Host 或空 Host 修补地址解析问题。

成功条件分别列：HTTP 状态、业务状态、必要结构与关键字段。不要为通过校验把预期 200 改成错误状态，也不要预设所有系统都用 `code: 0`。合法的零余额、空数组按契约判断。

## 4. 前后置处理一次说明完整

### 必填处理器矩阵

| 处理 | 放置位置 | 顺序/触发条件 | 完整脚本或字段提取规则 | 本级启用 | 子级默认启用 | 实际步骤继承/覆盖 | 保存位置 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 认证准备（需要时） | 项目/目录/接口/独立步骤等具体位置 | 明确在谁之前、每轮还是一次 | 按真实响应生成 | 明确 | 明确 | 明确 | 环境/运行变量及保存设置 |
| 响应断言与提取 | 指定接口或场景步骤的后置处理 | 先验证，后更新有效变量 | 完整代码或 JSONPath | 明确 | 明确 | 明确 | 具体作用域 |
| 业务断言/清理（需要时） | 具体步骤 | 依赖与失败分支 | 完整规则 | 明确 | 明确 | 明确 | 说明副作用 |

“脚本内容存在”“处理器启用”“上级对子级的默认状态”“实际子级是否显式开启/关闭”“该场景是否引用了这份用例”要分别核对。默认关闭不等于所有子级关闭；默认开启也不能证明子级覆盖后仍开启。目录继承按层级生效，执行顺序需要结合目录/接口/场景的实际配置核对。[S3]

给出的脚本交付格式：

1. 文件或界面位置，所属环境/目录/用例/步骤。
2. “整体替换现有哪段”或“追加到哪一位置”，以及要移除的重复提取器/脚本。
3. 完整代码，所有变量名与配置表一致，不能省略必须的辅助函数。
4. 启用、本级/子级、实际步骤覆盖与保存设置的建议值。
5. 执行前条件、成功后变量、失败时的行为和核验方式。

认证后置处理须检查状态、业务结果、字段存在、非空与格式后再写值。响应字段可能在根节点或 `data` 内，以资料为准；不能套一个万能字段路径。若 refresh 字段按契约可省略，明确“保留旧值”的条件；否则缺失即停止更新并报明原因。禁止失败时写 `undefined`、空串或旧示例值。

不同层级使用同名写入时须审查最后由谁覆盖。全局/目录脚本包含认证准备时，排除认证请求自身递归触发和无关请求。不要在性能循环中无条件刷新每个用户共用的轮换凭据。

## 5. 场景步骤、引用与同步

把真实依赖按顺序列出：必要初始化 → 认证或读取有效凭据 → 取业务标识（需要时）→ 目标业务请求 → 必要清理。说明认证失败时哪些步骤应停止或跳过，不能继续用空值请求业务接口。独立请求已有有效环境数据时可单独运行，无须机械重跑全部认证链。

| 添加方式 | 适用目的 | 必须交代 |
| --- | --- | --- |
| 引用已有接口/用例 | 需要跟随来源维护与同步 | 具体引用对象、哪些字段同步、编辑可能影响哪份来源、场景覆盖项；用一次无副作用检查确认当前同步行为 |
| 复制或独立步骤 | 需要隔离修改或固定本次配置 | 不会当然跟随以后调试修改；来源变化后怎样显式同步/更新 |

Apifox 提供接口/用例与步骤的数据同步能力；引用模式可影响同步与编辑行为，具体应按当前版本及所选模式核对。不要把“勾选引用”当作通用必选项，也不能保证取消引用后仍自动同步。[S4]

明确：来源调试是否保存、场景是否保存、运行选了哪个环境、实际步骤是否启用，以及运行的是否正是刚修改的版本。引用并不替代变量初始化或处理器启用检查。

## 6. 功能验收与交付

- 查看实际解析后的方法、URL、参数和鉴权；无意外空值、无残留占位符。
- 用必要的最少请求验证单接口与场景的 HTTP、业务断言和数据关联。
- 认证成功产生新凭据后先确认最新值已保留，再排查后续失败。观察多轮功能稳定性时，避免无必要重复轮换；对必须轮换的流程按确认的顺序和次数验证。
- 将修改清单、完整脚本和环境配置一起交付。需要导入时列出文件、目标项目/模块、匹配规则、覆盖范围、是否包含环境与场景；以真实导出结构和导入预览为准。若仅修改了本地文件，写明尚未导入 Apifox。
- 保存当前可用版本，确认后才清理旧文件；不要同时启用新旧 Token 提取逻辑。
